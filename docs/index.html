Which PFTL API methods expose public keys, signatures, or signing capability to an unauthenticated caller; which are gated to ADMIN; and how the surface should migrate to post-quantum signatures.

All 74 JSON-RPC methods were probed live from an unauthenticated client on 2026-11-13T20:57:45Z: 32 succeeded, 19 returned an RPC error, 23 were refused with HTTP 403 Forbidden, 0 failed at transport. Migration verdict

The signing entry points (sign, sign_for, channel_authorize, and the deprecated submit signing path) must gain hybrid classical + ML-DSA signing before a cryptographically relevant quantum computer exists, because every signature they produce is recorded on the public ledger forever. The read surface (account_tx, tx, ledger, transaction_entry, tx_history) needs no migration — it only relays what the ledger already records — but its consumers must be ready to verify ML-DSA signatures. The ADMIN gate is the only thing standing between an unauthenticated caller and wallet_propose / validation_create secret generation: it is enforced in code (RPCHandler.cpp:166) but depends on per-port configuration (admin nets, admin_user / admin_password), so it must be audited per deployment, not assumed. Full design, phased plan, costs and rollback notes: migration_design.md.

Scope and limits

All probe counts describe one unauthenticated probe run against the public endpoint on the fetch date above. The gRPC surface (4 methods) and the WebSocket subscription streams were inventoried from code only: the gRPC and WebSocket ports are not reachable from the audit machine. The origin server's TLS configuration is not observable from this machine (egress proxy re-signs the certificate). No secret, seed or passphrase was ever sent to the endpoint. See assumptions.md for the full list.
